«H2»6.1 CONCLUSION
«BODY»This mini project designed and implemented Code2Graph, a code-intelligence toolkit that converts a source tree into a navigable graph and keeps that graph consistent with the files on disk while a developer works. The pipeline of detection, extraction, graph construction, clustering, analysis, reporting and export is deterministic, uses tree-sitter and no neural model for structural extraction, and builds the code graph with no model credits. The MCP server makes the graph available to coding agents through tools for natural-language queries, shortest-path search, node, neighbour and community inspection, and broken-reference reporting.
«BODY»The distinctive feature of the system is real-time healing. A background watcher debounces file events, re-parses only the changed files, records edges whose endpoints disappeared as BROKEN with the missing node, its location and the reason, and restores them when their targets return or when a unique same-file, same-location match identifies a rename. This removes the manual update step for normal edits, deletions and renames and prevents the graph from silently drifting away from the code. In the controlled experiment of Section 5.4, deleting a file produced five broken references and restoring the file healed all five, returning the file status to HEALTHY without any manual edit of the graph.
«BODY»The measurements taken for this report show that the approach is practical. Applied to its own repository, the implementation converted 566 code files into 15,217 nodes and 35,451 edges in twenty-three seconds with no model calls, clustered them into 615 communities in nine seconds, and classified 97.2 per cent of the edges as directly extracted from the source. Its automated suite reports 6,542 passing tests with 80 per cent statement coverage, and the modules that carry the central behaviour are covered at 85 to 91 per cent. The published evaluation of the upstream project, quoted as external evidence, reports competitive retrieval recall and an improvement in key-fact coverage on a one-million-line repository.
«BODY»In terms of the Sustainable Development Goals, the mini project primarily supports SDG 9 by contributing an innovative, locally runnable tool to the technological capability of software teams, and it supports SDG 4, SDG 8, SDG 12 and SDG 17 as described in Chapter 1. Beyond the specific numbers, the most transferable lesson of the work is a design principle: a tool that supports maintenance should record what it does not know. A broken reference, a flagged document, a truncated answer and a refused write are all first-class outcomes in this system, and that is what makes its answers safe to rely on.
«H2»6.2 FUTURE ENHANCEMENT
«BODY»The project is experimental, and its command surface and metadata may still change. The following enhancements are proposed.
«BULLET»Semantic extraction for documents and images: a configured model could be used for PDFs and images that are currently only flagged, with the output clearly labelled as AMBIGUOUS or INFERRED and kept separate from the deterministic layer.
«BULLET»More languages: the documented extractor procedure allows further tree-sitter languages to be added, each with a fixture and behavioural tests; the seven files that contributed nothing in this measurement would be the first candidates.
«BULLET»Larger healing evaluation: the deletion and rename experiment should be repeated on a large repository with an instrumented watcher, reporting the number of broken references per edit, the healing rate and the false-healing rate.
«BULLET»Stable interfaces: the MCP schemas and the graph metadata could be frozen and versioned for a first stable release, together with a final project name.
«BULLET»Richer visualisation: interactive views of communities, import cycles and broken references could be added to the HTML export, together with editor integration so that a broken reference is visible where the code is edited.
«BULLET»Impact analysis in continuous integration: the graph-difference function could be combined with the pull-request tooling to report, for each change, which nodes and communities are affected.
«BULLET»Team and cloud use: the HTTP transport could be extended with authentication, per-team graphs and a shared store through the existing Cypher export, which already targets Neo4j and FalkorDB.
«BULLET»Query quality: the lexical seed selection could be extended with a local embedding model behind an optional flag, keeping the default installation free of model dependencies.

«H2»APPENDIX 4 - KNOWN ISSUES OF THE REPOSITORY
«BODY»The verification performed for this report also found issues in the repository that are unrelated to the design claims but relevant to anyone who installs it. They are recorded here so that the next contributor does not rediscover them.
«BULLET»The package metadata declares LICENSE, LICENSE-MIT and NOTICE files that are not present in the repository, so a wheel build succeeds but ships no license text.
«BULLET»The Markdown extractor imports PyYAML when it is available and silently falls back to a flat parser otherwise; PyYAML is not a declared runtime dependency, so nested frontmatter keys are lost in a minimal installation.
«BULLET»The Terraform tests require tree-sitter-hcl, which is listed in the development group and in an optional extra but not in the base install; without it, thirty-two tests fail with an assertion on an empty extraction rather than a dependency message.
«BULLET»The continuous-integration workflow runs the suite and the generated-artefact check but treats the static security scan and the dependency audit as non-blocking, and it does not run a coverage floor.
«BULLET»The command-line dispatcher is a single function of about 3,900 lines and is covered at 56 per cent, which is the main obstacle to further testing of the interface layer.
