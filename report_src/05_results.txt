«H2»5.3 RESULTS AT REPOSITORY SCALE
«BODY»The first measurement applies the toolkit to its own source tree. The command code2graph extract . --code-only --no-cluster scanned 566 code files and wrote a graph of 15,217 nodes and 35,451 edges in 23 seconds, using two worker processes and no model calls. A subsequent cluster-only run produced 615 communities in nine seconds. Table 5.2 summarises the result.

«H2»5.4 THE HEALING EXPERIMENT
«BODY»The central claim of the mini project is that a graph can survive edits without manual rebuilding and without losing the information that a reference once existed. To test the claim directly, a controlled experiment was performed on a two-file demonstration project. The project contains a module app/core.py that defines parse_config() and load(), and a module app/service.py that imports parse_config() and calls it. The graph before the experiment contains five nodes and seven edges. Table 5.3 lists the steps and the observed state after each of them.
«CAP»Table 5.3 Healing experiment on a two-file project
«TBL»5.3
«BODY»When app/core.py was deleted and code2graph update . was run, the rebuild reported three nodes and two edges, and the graph file recorded five BROKEN references: two containment edges inside the deleted file, one call edge between its two functions, and two cross-file edges from app/service.py, namely the import edge and the call edge. Each record names the missing node, its file and line, the reason, and the affected files, as shown in Figure 5.9.
«FIG»fig5_8_broken.png|Figure 5.9 Broken references after deleting a file
«BODY»When the file was restored and update was run again, all five records transitioned to HEALED and the active broken count returned to zero. The heal_status tool reported the file as HEALTHY with zero broken and five healed references, as shown in Figure 5.10. The graph returned to five nodes and seven edges, and the cross-file references from app/service.py were restored to their original endpoints. Figure 5.11 plots the three states of the experiment.
«FIG»fig5_9_healed.png|Figure 5.10 Healing status after restoring the file
«FIG»fig5_7_healing_cycle.png|Figure 5.11 State of the graph across the healing cycle
«BODY»Three observations follow. First, the information was not lost: the record kept the original edge attributes, the missing node snapshot and the reason, so a later reader can see what used to depend on the deleted symbol. Second, no phantom node was created to hold the dangling edge, so a query over the graph could not accidentally traverse to a symbol that does not exist. Third, the whole cycle required no manual editing of the graph file and no model call, and each update completed in well under a second. The demonstration is small by design, but it exercises exactly the transitions that the test suite asserts in larger projects, where the same code path also handles renames by location match.
«H2»5.5 ENGINEERING QUALITY OF THE MINI PROJECT
«BODY»Correct behaviour of a tool of this size cannot be argued from a demonstration alone, so the implementation was verified with its own automated suite. In a clean virtual environment on the two-core machine, pytest tests/ -q reported 6,542 passing tests, 174 skipped tests and zero failures in 119 seconds. A coverage run over the same suite reported 80 per cent statement coverage across 40,724 statements in 95 modules. The skips are caused by optional grammars and platform-specific paths, not by disabled assertions.
«BODY»The distribution of coverage is more informative than the total. The modules on the critical path are well covered: extract 91 per cent, engine 91 per cent, build 90, analyse 95, report 96, wiki 99, watch 85 and healing 85. The weakest modules are the command-line dispatcher at 56 per cent, the pull-request triage module at 36 per cent, and a group of optional language extractors between 2 and 27 per cent, because the corresponding grammars were not installed in the measuring environment. Figure 5.12 shows the same verification as a run: the generated-artefact check passes for all 134 artefacts and the linter passes with the repository's committed rule set.
«FIG»fig5_11_quality_gates.png|Figure 5.12 Verification gates
«BODY»Two regression guards deserve a separate mention because they protect the properties that this report claims. The architecture-document test imports every symbol that the design chapter names, so the documentation cannot silently describe a function that does not exist. The incremental-equivalence tests rebuild a project twice, once from a cold cache and once incrementally, and assert that the two graphs are identical, which is the property that makes the healing mechanism trustworthy.

«H2»5.8 DISCUSSION AND LIMITATIONS
«BODY»The results support three observations. First, a deterministic structural pipeline is fast enough to be practical: half a thousand files become a thirty-five-thousand-edge graph in twenty-three seconds on two cores, with no API key and no cost. Second, the healing mechanism behaves as designed on the transitions that matter, namely deletion and restoration, and it preserves evidence instead of discarding it. Third, the engineering quality of the implementation is measurable and adequate for a mini project: a large automated suite, high coverage of the critical path, and two guards that protect the documented design from drifting away from the code.
«BODY»The results also have limits, and stating them is part of the contribution. The healing experiment uses a two-file project; the same code path is exercised by the repository's own tests on larger projects, but no large-scale field measurement was made here. The graph reflects the languages for which grammars were installed: seven files in this repository contributed nothing to the graph because an optional grammar was missing, and the tool reports that fact rather than silently ignoring it. Python is over-represented in the measurement because the measured repository is written in Python. The query engine is lexical and graph-based, not semantic, so a question whose wording shares no vocabulary with the code will retrieve weak seeds. Finally, the published benchmark numbers in Section 5.6 are third-party and were not reproduced.
