«H2»1.1 OVERVIEW OF THE MINI PROJECT
«BODY»Modern software systems are rarely small. A typical production repository contains thousands of files, tens of thousands of functions and classes, and an even larger number of relationships between them: one module imports another, one function calls another, one class inherits from another. Understanding how a change in one place ripples through the rest of the system is one of the most time-consuming activities in software engineering. The same difficulty now affects AI coding assistants, which must decide what to read from a repository before they can answer a question or edit a file.
«BODY»This mini project, Code2Graph, addresses that problem by converting a source tree into a navigable knowledge graph. In the graph, symbols, files, imports, calls, inheritance links and other relationships are modelled as nodes and edges. Instead of repeatedly scanning the entire project, a developer or a coding agent can query the graph to follow execution paths, understand dependencies and identify the impact of a change.
«BODY»The system is implemented as a Python library together with a Model Context Protocol (MCP) server. The library runs a staged pipeline of detection, extraction, graph construction, clustering, analysis, reporting and export. The MCP server loads the generated graph, answers graph queries from coding agents, and runs a background watcher that keeps the graph current while the developer works. File saves, deletions and renames are detected automatically; only the affected files are re-parsed; references whose targets have disappeared are recorded as broken rather than silently discarded; and those references are restored automatically when their targets return. This behaviour is called real-time healing and it is the central contribution of the mini project.
«BODY»A second design decision is that the structural indexing of source code is fully deterministic. Files are parsed with tree-sitter grammars, and the resulting graph depends only on the bytes of the source files and the installed grammar versions. Building the code graph therefore consumes no large-language-model credits, needs no API key, works offline, and produces the same graph on every machine. Files that genuinely need semantic interpretation, such as PDFs and images, are detected and flagged for an optional external extraction workflow instead of being given invented content.
«BODY»The mini project is implemented in Python, is installable with pip, ships a command-line interface with twenty-seven command branches, an MCP server with twelve tools and six resources, thirty-six language extractor modules covering 112 file extensions, and a test suite of 6,542 tests. All numbers quoted in this report were measured on the implementation described in Chapter 4.
«H2»1.2 PROBLEM STATEMENT
«BODY»Developers and AI coding agents face several related problems when working with large code bases.
«BULLET»Navigation cost: finding where a symbol is defined, who calls it and what depends on it normally requires text search followed by manual reading of many files, and the effort grows with the size of the repository.
«BULLET»Context limits of LLM agents: an assistant can only reason about the text placed in its context window. Packing a whole repository into every request is expensive and inaccurate, while grep-style searching returns many irrelevant matches and needs many turns.
«BULLET»Stale indexes: static code indexes become outdated as soon as files are edited. A stale index silently returns references to symbols that were renamed or deleted, which is worse than returning nothing, because the user trusts the answer.
«BULLET»Loss of information on change: tools that rebuild an index from scratch after every edit are slow, and tools that simply drop dangling links lose the information that something used to be connected.
«BULLET»Cost and dependence on external services: many semantic-retrieval and memory systems require a model call for every document they ingest, which increases cost, latency and dependence on a paid API.
«BODY»The problem addressed in this mini project is therefore to design and implement a code-intelligence system that (i) represents a code base as a queryable graph, (ii) exposes this graph to coding agents through a standard protocol, (iii) keeps the graph consistent with the files on disk without any manual update command, and (iv) does all of this deterministically, locally and cheaply.
«H2»1.3 OBJECTIVES OF THE MINI PROJECT
«BODY»The overall objective is to build an experimental, open and locally runnable code-intelligence layer that lets developers and AI agents understand large repositories through graph queries rather than repeated file scanning. The specific objectives are listed below.
«BULLET»To detect and classify the files of a project and to extract symbols and relationships from them with tree-sitter based extractors that cover a broad set of programming languages.
«BULLET»To store the extracted knowledge in a NetworkX graph with a validated schema, and to label every relationship with a confidence level: EXTRACTED, INFERRED or AMBIGUOUS.
«BULLET»To group the graph into communities and to compute analyses such as highly connected nodes, surprising connections, import cycles and differences between two graphs.
«BULLET»To generate human-readable and machine-readable outputs: GRAPH_REPORT.md, an interactive HTML graph, a per-community Markdown wiki, a Mermaid call-flow page, and exports to JSON, SVG, GraphML, Obsidian, Canvas and Cypher.
«BULLET»To expose the graph through an MCP server whose tools support natural-language queries, shortest-path search, node and neighbour inspection, community lookup and broken-reference reporting.
«BULLET»To implement a background watcher that debounces file events, re-parses only changed files, records broken edges and restores them when their targets reappear, including healing across a unique symbol rename.
«BULLET»To enforce input safety for URLs, fetched content, graph file paths and node labels.
«BULLET»To verify the implementation with an automated test suite and to measure the behaviour of the system on a real repository and on a controlled experiment.
«H2»1.4 SCOPE OF THE MINI PROJECT
«BODY»The scope covers the complete life cycle of a code graph: its creation from a source tree, its use by humans and agents, and its maintenance while the source tree changes. The mini project concentrates on structural code intelligence. Semantic extraction from non-code artefacts, such as PDFs and images, is deliberately outside the deterministic core and is flagged rather than guessed. Benchmarking against other retrieval systems is outside the implemented scope of the mini project; where the upstream project publishes such numbers, they are quoted as external evidence and labelled as such in Chapter 5.
«H3»1.4.1 EXISTING SYSTEM
«BODY»Existing approaches to understanding a code base fall into four groups. The first group consists of plain text tools such as grep and find, which are fast and universal but know nothing about program structure. The second group consists of IDE features and language servers that provide go-to-definition and find-references for one language at a time, usually inside a single editor session. The third group consists of tag indexes and code-search platforms that index a repository and return matches, but rarely expose a graph that an AI agent can traverse, and often have to be fully re-indexed after large changes. The fourth group consists of LLM-based retrieval and memory systems that embed or summarise documents, usually at the price of a model call per document.
«BODY»These systems have clear limitations for agent-driven development. Text search does not understand relationships; editor-bound language servers are not designed to be queried by external agents; static indexes go stale; and LLM-based ingestion is costly and non-deterministic. When a file is deleted or a symbol is renamed, most tools either return outdated references or forget that the references ever existed.
«H3»1.4.2 PROPOSED SYSTEM
«BODY»The proposed system builds a graph of the code base once and then maintains it incrementally. The pipeline runs in the order detect, extract, build, cluster, analyse, report and export. Each stage is a separate module and the stages communicate through plain Python dictionaries and NetworkX graphs, which keeps the interfaces small and every stage independently testable.
«BODY»The MCP server loads the generated graph into memory and offers query tools to coding agents. In the background, a watcher monitors the project directory. When a file changes, only that file is re-parsed and the new node set is compared with the old one. Edges whose endpoints disappeared are kept as BROKEN metadata with the missing node, its location and the reason. If the node comes back, the edge is restored; if a symbol is renamed in the same file and at the same location, a unique match can heal the reference. The graph is then persisted atomically and the in-memory copy in the MCP server is refreshed. As a result there is no manual update step for normal code edits, deletions or renames.

«H2»1.5 RELEVANCE TO THE SOCIETY
«BODY»Software underpins healthcare, finance, education, transport and public administration. The people who maintain this software spend a large share of their time reading and understanding existing code rather than writing new code. Tools that shorten this understanding phase improve productivity, reduce defects caused by misunderstood dependencies, and lower the barrier for newcomers who join a project.
«BODY»Code2Graph is relevant to society in five ways. First, it makes large code bases easier to learn, which benefits students, junior developers and open-source contributors. Second, by reducing the amount of text that an AI assistant must read for each question, it lowers the computing resources consumed per query. Third, because the code graph is built locally and without a language model, organisations can analyse proprietary code without sending it to an external service. Fourth, by recording broken references explicitly, the system supports safer maintenance and refactoring and reduces the risk of failures in deployed systems. Fifth, the mini project builds on open standards, namely the Model Context Protocol, tree-sitter and NetworkX, and therefore contributes to an open ecosystem of developer tools.

«H3»1.6.1 SDG 9 - INDUSTRY, INNOVATION AND INFRASTRUCTURE (PRIMARY)
«BODY»SDG 9 calls for resilient infrastructure, inclusive industrialisation and the fostering of innovation. Target 9.5 asks countries to enhance scientific research and to upgrade the technological capabilities of industrial sectors, including by encouraging innovation. Digital infrastructure is built from software, and the cost of maintaining that software grows with its size. Code2Graph contributes an innovative developer-tooling layer: it turns a code base into a graph, keeps the graph accurate while the code changes, and makes the result available to both people and AI agents through an open protocol. This improves the technological capability of software teams and supports the reliable evolution of the digital infrastructure on which industries depend.
«H3»1.6.2 SDG 4 - QUALITY EDUCATION (SECONDARY)
«BODY»Target 4.4 aims to increase the number of people with relevant technical skills. Learning to read an unfamiliar repository is a core skill for students and early-career engineers. The generated GRAPH_REPORT.md, the per-community wiki and the Mermaid call-flow pages give learners a structured overview of a project, and the highly connected nodes and communities point to the parts of the system worth studying first.
«H3»1.6.3 SDG 8 - DECENT WORK AND ECONOMIC GROWTH (SECONDARY)
«BODY»Target 8.2 refers to higher economic productivity through technological upgrading and innovation. By reducing the time that engineers and AI assistants spend searching for code, and by warning about references that were broken by an edit, the mini project raises the productivity of software work. Fewer wasted hours and fewer regressions translate into lower maintenance cost for small companies and independent developers alike.
«H3»1.6.4 SDG 12 - RESPONSIBLE CONSUMPTION AND PRODUCTION (SUPPORTING)
«BODY»SDG 12 is concerned with doing more with fewer resources. The mini project does not address material consumption directly, but it follows the same spirit of efficiency: the graph is built without model calls, only changed files are re-parsed, and an agent can retrieve a small relevant subgraph instead of loading a whole repository into every request. In the measurements of Chapter 5 the full graph of this repository is built in 23 seconds with no model credits, and an incremental update of a two-file project completes in under one second.
«H3»1.6.5 SDG 17 - PARTNERSHIPS FOR THE GOALS (SUPPORTING)
«BODY»Target 17.6 encourages cooperation on, and access to, science, technology and innovation, together with knowledge sharing. Code2Graph is published as an open repository and is built on open standards and libraries. Its extractor architecture allows new language extractors to be contributed as separate modules, and its MCP interface allows any compatible client to use it. This supports collaboration and knowledge sharing among developers and researchers.
«BODY»The remaining goals are not directly addressed by this mini project, and the report makes no claim of such an impact.
