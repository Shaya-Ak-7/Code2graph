5.5 ENGINEERING QUALITY OF THE MINI PROJECT
Correct behaviour of a tool of this size cannot be argued from a demonstration alone, so the implementation was verified with its own automated suite. In a clean virtual environment on the two-core machine, pytest tests/ -q reported 6,542 passing tests, 174 skipped tests and zero failures in 119 seconds. A coverage run over the same suite reported 80 per cent statement coverage across 40,724 statements in 95 modules. The skips are caused by optional grammars and platform-specific paths, not by disabled assertions.
The distribution of coverage is more informative than the total. The modules on the critical path are well covered: extract 91 per cent, engine 91 per cent, build 90, analyse 95, report 96, wiki 99, watch 85 and healing 85. The weakest modules are the command-line dispatcher at 56 per cent, the pull-request triage module at 36 per cent, and a group of optional language extractors between 2 and 27 per cent, because the corresponding grammars were not installed in the measuring environment. 5.8 DISCUSSION AND LIMITATIONS
The results support three observations. First, a deterministic structural pipeline is fast enough to be practical: half a thousand files become a thirty-five-thousand-edge graph in twenty-three seconds on two cores, with no API key and no cost. Second, the healing mechanism behaves as designed on the transitions that matter, namely deletion and restoration, and it preserves evidence instead of discarding it. Third, the engineering quality of the implementation is measurable and adequate for a mini project: a large automated suite, high coverage of the critical path, and two guards that protect the documented design from drifting away from the code.
The results also have limits, and stating them is part of the contribution. The healing experiment uses a two-file project; the same code path is exercised by the repository's own tests on larger projects, but no large-scale field measurement was made here. The graph reflects the languages for which grammars were installed: seven files in this repository contributed nothing to the graph because an optional grammar was missing, and the tool reports that fact rather than silently ignoring it. Python is over-represented in the measurement because the measured repository is written in Python. The query engine is lexical and graph-based, not semantic, so a question whose wording shares no vocabulary with the code will retrieve weak seeds. Finally, the published benchmark numbers in Section 5.6 are third-party and were not reproduced.

CONCLUSION AND FUTURE ENHANCEMENT
6.1 CONCLUSION
This mini project designed and implemented Code2Graph, a code-intelligence toolkit that converts a source tree into a navigable graph and keeps that graph consistent with the files on disk while a developer works. The pipeline of detection, extraction, graph construction, clustering, analysis, reporting and export is deterministic, uses tree-sitter and no neural model for structural extraction, and builds the code graph with no model credits. The MCP server makes the graph available to coding agents through tools for natural-language queries, shortest-path search, node, neighbour and community inspection, and broken-reference reporting.
The distinctive feature of the system is real-time healing. A background watcher debounces file events, re-parses only the changed files, records edges whose endpoints disappeared as BROKEN with the missing node, its location and the reason, and restores them when their targets return or when a unique same-file, same-location match identifies a rename. This removes the manual update step for normal edits, deletions and renames and prevents the graph from silently drifting away from the code. In the controlled experiment of Section 5.4, deleting a file produced five broken references and restoring the file healed all five, returning the file status to HEALTHY without any manual edit of the graph.
The measurements taken for this report show that the approach is practical. Applied to its own repository, the implementation converted 566 code files into 15,217 nodes and 35,451 edges in twenty-three seconds with no model calls, clustered them into 615 communities in nine seconds, and classified 97.2 per cent of the edges as directly extracted from the source. Its automated suite reports 6,542 passing tests with 80 per cent statement coverage, and the modules that carry the central behaviour are covered at 85 to 91 per cent. The published evaluation of the upstream project, quoted as external evidence, reports competitive retrieval recall and an improvement in key-fact coverage on a one-million-line repository.
In terms of the Sustainable Development Goals, the mini project primarily supports SDG 9 by contributing an innovative, locally runnable tool to the technological capability of software teams, and it supports SDG 4, SDG 8, SDG 12 and SDG 17 as described in Chapter 1. Beyond the specific numbers, the most transferable lesson of the work is a design principle: a tool that supports maintenance should record what it does not know. A broken reference, a flagged document, a truncated answer and a refused write are all first-class outcomes in this system, and that is what makes its answers safe to rely on.
6.2 FUTURE ENHANCEMENT
The project is experimental, and its command surface and metadata may still change. The following enhancements are proposed.
Semantic extraction for documents and images: a configured model could be used for PDFs and images that are currently only flagged, with the output clearly labelled as AMBIGUOUS or INFERRED and kept separate from the deterministic layer.
More languages: the documented extractor procedure allows further tree-sitter languages to be added, each with a fixture and behavioural tests; the seven files that contributed nothing in this measurement would be the first candidates.
Larger healing evaluation: the deletion and rename experiment should be repeated on a large repository with an instrumented watcher, reporting the number of broken references per edit, the healing rate and the false-healing rate.
Stable interfaces: the MCP schemas and the graph metadata could be frozen and versioned for a first stable release, together with a final project name.
Richer visualisation: interactive views of communities, import cycles and broken references could be added to the HTML export, together with editor integration so that a broken reference is visible where the code is edited.
Impact analysis in continuous integration: the graph-difference function could be combined with the pull-request tooling to report, for each change, which nodes and communities are affected.
Team and cloud use: the HTTP transport could be extended with authentication, per-team graphs and a shared store through the existing Cypher export, which already targets Neo4j and FalkorDB.
Query quality: the lexical seed selection could be extended with a local embedding model behind an optional flag, keeping the default installation free of model dependencies.

APPENDIX 4 - KNOWN ISSUES OF THE REPOSITORY
The verification performed for this report also found issues in the repository that are unrelated to the design claims but relevant to anyone who installs it. They are recorded here so that the next contributor does not rediscover them.
The package metadata declares LICENSE, LICENSE-MIT and NOTICE files that are not present in the repository, so a wheel build succeeds but ships no license text.
The Markdown extractor imports PyYAML when it is available and silently falls back to a flat parser otherwise; PyYAML is not a declared runtime dependency, so nested frontmatter keys are lost in a minimal installation.
The Terraform tests require tree-sitter-hcl, which is listed in the development group and in an optional extra but not in the base install; without it, thirty-two tests fail with an assertion on an empty extraction rather than a dependency message.
The continuous-integration workflow runs the suite and the generated-artefact check but treats the static security scan and the dependency audit as non-blocking, and it does not run a coverage floor.
The command-line dispatcher is a single function of about 3,900 lines and is covered at 56 per cent, which is the main obstacle to further testing of the interface layer.
