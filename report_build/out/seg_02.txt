Code2Graph is relevant to society in five ways. First, it makes large code bases easier to learn, which benefits students, junior developers and open-source contributors. Second, by reducing the amount of text that an AI assistant must read for each question, it lowers the computing resources consumed per query. Third, because the code graph is built locally and without a language model, organisations can analyse proprietary code without sending it to an external service. Fourth, by recording broken references explicitly, the system supports safer maintenance and refactoring and reduces the risk of failures in deployed systems. Fifth, the mini project builds on open standards, namely the Model Context Protocol, tree-sitter and NetworkX, and therefore contributes to an open ecosystem of developer tools.

CHAPTER 2
LITERATURE REVIEW
This chapter reviews the work most closely related to the mini project. The review is organised by theme: graph representations of programs, parsing infrastructure, community detection, retrieval for language-model agents, long-term memory benchmarks, lexical, dense and fused retrieval, and the Model Context Protocol. The final section summarises the reviewed work and states the gap that the mini project addresses.
2.1 GRAPH REPRESENTATIONS OF SOURCE CODE
2.1.1 YAMAGUCHI, GOLDE, ARP AND RIECK (2014) - CODE PROPERTY GRAPHS
Yamaguchi et al. (2014) introduced the code property graph, a joint representation that merges the abstract syntax tree, the control-flow graph and the program-dependence graph of a program into one data structure. Vulnerability patterns are then expressed as graph traversals, so that a single query can combine syntactic, control-flow and data-dependence conditions. The work showed that a graph is a natural substrate for large-scale program analysis. Code2Graph shares the idea that a code base is queryable data, but it targets general code understanding rather than vulnerability discovery, and it concentrates on the relationships that can be extracted quickly for many languages: containment, imports, calls and inheritance.
2.1.2 ALLAMANIS, BROCKSCHMIDT AND KHADEMI (2018) - LEARNING TO REPRESENT PROGRAMS WITH GRAPHS
Allamanis et al. (2018b) represented programs as graphs whose edges capture both syntactic structure and semantic relations such as data flow, and applied gated graph neural networks to tasks such as variable-misuse detection. Their results showed that explicit relational structure helps a model reason about code better than a flat token sequence. For this mini project the relevance is the confirmation that relations between program elements are valuable features. Code2Graph stores such relations explicitly and exposes them to downstream agents instead of training a neural model on them, which keeps the pipeline deterministic and cheap.
2.1.3 ALLAMANIS, BARR, DEVANBU AND SUTTON (2018) - MACHINE LEARNING FOR BIG CODE AND NATURALNESS
The survey by Allamanis et al. (2018a) reviews probabilistic models of source code and the naturalness hypothesis, which states that software is repetitive and predictable in ways similar to natural language. The survey also discusses the importance of program structure and of tools that support code search, summarisation and navigation. It provides the research background for treating code as a corpus that can be indexed, queried and used as context for learned models.
2.2 PARSING AND LANGUAGE TOOLING
2.2.1 TREE-SITTER
Tree-sitter is a parser generator and an incremental parsing library that builds a concrete syntax tree for a source file and can update that tree efficiently as the file is edited (Brunsfeld et al., n.d.). It is written in C, tolerates syntax errors, and has grammars for a large number of programming languages. Code2Graph uses tree-sitter as its deterministic extraction mechanism: each language extractor parses a file, walks the syntax tree to collect nodes and edges, and then performs a call-graph second pass to add inferred call relations. In the measured run reported in Chapter 5, the implementation parses 566 files of its own repository with twenty grammar packages and produces 35,451 edges.
2.2.2 LANGUAGE SERVER PROTOCOL
The Language Server Protocol (Microsoft, n.d.) defines how an editor communicates with a language-specific server that provides features such as go-to-definition, find-references and diagnostics. Language servers give precise answers for one language and a running editor session, but they are not designed as a language-independent, persistent graph that an external agent can traverse and that survives across sessions. Code2Graph complements language servers by offering a cross-language graph with explicit confidence labels and a stored history of broken references.
2.2.3 NETWORKX
NetworkX is a Python package for the creation, manipulation and study of the structure, dynamics and functions of complex networks (Hagberg, Schult and Swart, 2008). It provides graph classes, traversal and shortest-path algorithms and readers and writers for many formats. Code2Graph uses NetworkX graphs as the in-memory representation passed between its build, cluster, analyse and export stages, and uses the same library inside the MCP server to answer traversal queries.
2.3 COMMUNITY DETECTION IN GRAPHS
Large graphs are easier to understand when they are divided into groups of densely connected nodes. Blondel et al. (2008) proposed the Louvain method, a fast heuristic that greedily optimises modularity and builds a hierarchy of communities. Traag, Waltman and van Eck (2019) showed that Louvain can produce badly connected or even disconnected communities and introduced the Leiden algorithm, which guarantees well-connected communities and is faster in practice. These works form the theoretical basis for modularity-based community detection. In Code2Graph the cluster stage takes a graph and returns a mapping from a community identifier to a list of node identifiers without mutating the graph. The communities are then used by the report generator, the per-community wiki and the community query tool of the MCP server. On this repository the stage produces 615 communities in nine seconds.
2.4 RETRIEVAL AND CODE CONTEXT FOR LLM AGENTS
2.4.1 RETRIEVAL-AUGMENTED GENERATION
Lewis et al. (2020) combined a pre-trained sequence-to-sequence generator with a non-parametric memory, a dense vector index over documents, so that the generator conditions on retrieved passages. The retrieval-augmented generation paradigm is now the standard way to supply knowledge that does not fit in a model's parameters or context window. Code2Graph supports this paradigm for code by offering a retrieval layer that returns relevant nodes and their neighbours with their source locations.
2.4.2 REPOCODER
Zhang et al. (2023) proposed RepoCoder, an iterative retrieval and generation framework for repository-level code completion, together with a benchmark for the task. Their study showed that retrieving relevant code from within the same repository improves completion quality, and that retrieval can be improved by using the model's own intermediate output to form a better query. This supports the idea that repository structure should be accessible to the model at inference time rather than being flattened into a prompt.
2.4.3 SWE-BENCH
Jimenez et al. (2024) introduced SWE-bench, a benchmark built from real GitHub issues and pull requests in popular Python repositories. A system must edit the code base so that the issue is resolved and the associated tests pass. The benchmark demonstrated that realistic software-engineering tasks require navigation across many files and long contexts, which is exactly the situation in which a dependency graph is useful.
2.5 LONG-TERM MEMORY FOR CONVERSATIONAL AGENTS
2.5.1 MEMGPT
Packer et al. (2023) described MemGPT, which borrows the idea of a memory hierarchy from operating systems to give a language model virtual context beyond its fixed window by moving information between fast and slow memory tiers. It illustrates that agent memory is a systems problem that depends on indexing and retrieval, not only on model quality.
2.5.2 LOCOMO AND LONGMEMEVAL
Maharana et al. (2024) created LOCOMO, a benchmark of very long multi-session conversations with question answering that tests whether an agent can recall and reason over earlier dialogue. Wu et al. (2025) created LongMemEval, a benchmark that evaluates chat assistants on information extraction, multi-session reasoning, temporal reasoning and knowledge updates. The upstream Code2Graph project uses both datasets to compare its graph-based retrieval with dedicated memory systems; those published numbers are quoted, with their source, in Section 5.6 of this report.
2.6 LEXICAL, DENSE AND FUSED RETRIEVAL
Robertson and Zaragoza (2009) describe BM25, a probabilistic ranking function that remains a strong lexical baseline. Dense retrievers embed queries and documents into a vector space; Chen et al. (2024) describe BGE-M3, a multilingual embedding model that supports dense retrieval of long texts and that is the shared embedder of the upstream benchmark harness. Cormack, Clarke and Buettcher (2009) proposed Reciprocal Rank Fusion, a simple method that merges several ranked lists by summing reciprocal rank scores, and showed that it outperforms individual rankers and several learning-to-rank methods. Cohen (1960) introduced the kappa statistic for agreement between two raters, which is used to validate a machine judge against a second independent judge. Among these techniques, the deterministic part of this mini project uses lexical matching over node labels, source paths and identifiers inside the query engine; the embedding-based baselines belong to the published evaluation, not to the deterministic graph build.
