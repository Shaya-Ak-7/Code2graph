2.7 MODEL CONTEXT PROTOCOL
The Model Context Protocol (Anthropic, 2024) is an open protocol that standardises how AI applications connect to external tools and data sources. A client discovers the tools offered by a server and calls them with structured JSON messages, and servers can be reached over standard input and output or over HTTP. By implementing its query layer as an MCP server, Code2Graph can be used from any MCP-compatible coding assistant without a custom integration. The server implemented in this mini project exposes twelve tools, including query_graph, shortest_path, get_node, get_neighbors, get_community, god_nodes, graph_stats, broken_references and heal_status, together with six resources that return the report, the graph statistics, the god nodes, the surprising connections, the confidence audit and the suggested questions.

2.9 RESEARCH GAP
The reviewed work shows that graphs are a powerful representation of code, that tree-sitter provides robust and incremental parsing, that retrieval improves model performance on repository tasks, and that MCP offers a standard way to deliver tools to agents. However, most graph-based program-analysis systems are built as batch analysers. They produce a graph once and do not describe what happens to the references in the graph when files are edited, renamed or deleted while an agent is working. Retrieval and memory systems, on the other hand, usually rely on model calls to ingest content and do not treat structural code relationships as first-class data.
The mini project fills this gap by combining four properties in one local toolkit: a deterministic, model-free structural extraction for many languages; a confidence-labelled graph with a validated schema; an MCP server that exposes graph queries to agents; and a real-time healing mechanism that records broken references and restores them when possible, instead of letting the graph silently drift away from the code. The distinguishing property is negative as much as positive: the system prefers to report a broken reference, or no edge at all, rather than to invent a relationship that the source does not support.

3.1 SYSTEM ARCHITECTURE
The architecture of Code2Graph has two cooperating parts. The first is a batch pipeline that converts a source tree into a graph and a set of reports. The second is a live service, the MCP server with its background watcher, that serves the graph to agents and keeps it synchronised with the files on disk. Both parts share the same graph file, graph.json, stored in an output directory named code2graph-out by default.
Figure 3.1 shows the batch pipeline. The pipeline is a chain of stages: detect, extract, build, cluster, analyse, report and export. Each stage lives in its own module and the stages communicate through plain Python dictionaries and NetworkX graphs. This keeps shared state to a minimum and allows every stage to be tested independently, although some extractors still depend on module-level state that describes the active scan root, which is documented in the repository's architecture notes.
[figure]
Figure 3.1 Code2Graph processing pipeline
The detect stage scans a directory and returns a summary that groups files into categories and reports counts such as total files and total words. The extract stage takes a list of file paths and returns a dictionary containing nodes and edges. The build stage merges one or more extraction dictionaries into a NetworkX graph. The cluster stage partitions the graph into communities. The analyse functions compute highly connected nodes, surprising connections, import cycles, suggested questions and differences between two graphs. The report stage turns the graph and its analysis into a Markdown report, and the export stage writes the graph in several formats.
Figure 3.2 shows the live service. A coding agent acting as an MCP client sends a tool call to the MCP server, which answers from an in-memory copy of the graph that is cached per project. In parallel, a watcher observes the project directory. When files change, the watcher debounces the events, re-parses the affected files, compares the previous and the new node sets, updates the persisted graph and marks the in-memory copy for reload. Queries therefore reuse the cached graph, and a reload happens only when the persisted graph changes.
[figure]
Figure 3.2 MCP server and real-time healing architecture
The architecture follows five design principles. Determinism: structural extraction uses tree-sitter and no neural model, so the same input always yields the same graph and no model credits are consumed. Incrementality: only changed files are re-processed and unchanged nodes stay in the cached graph. Transparency: every edge carries a confidence label and every broken edge records why it is broken. Safety: all external input passes through a dedicated security module. Modularity: new languages and new export formats are added as separate functions or modules without changing the rest of the pipeline.
Figure 4.1 in the implementation chapter presents the same system as five layers, which is convenient when reading the source tree: an interface layer, an intelligence layer, a graph layer, an extraction layer and a foundation layer. The dependency rule is that a layer may use the layers below it and never the layers above it; paths, security and ids are the only modules imported by every layer.

3.3.1 DETECTION MODULE
The detection module walks the project directory and classifies every file by category: source code, documentation, papers and images. It returns a scan summary with the grouped files, the total number of files, the total word count, an optional warning and the scan root. The summary lets the rest of the pipeline decide which extractors apply and lets the user judge the size of the corpus before processing starts. Code files are handled by local structural extractors, while documents and images that need semantic interpretation are flagged for an external workflow.
3.3.2 EXTRACTION MODULE
The extraction module is the front end of the pipeline. It accepts a list of paths and dispatches each file to a language-specific extractor according to its suffix, with an additional dispatch table for scripts that carry a shebang but no extension. A helper, collect_files, expands a directory into such a list. Each extractor parses its file with tree-sitter, walks the syntax tree, collects nodes for symbols and files, and collects edges for relations such as containment, imports, calls and inheritance. A second pass resolves calls across the call graph and emits inferred call edges. Every extractor returns the same schema, so downstream stages do not need to know which language produced a result. Node identifiers and source_file values are derived relative to a root directory, so the root should always be passed explicitly.
3.3.3 GRAPH CONSTRUCTION AND VALIDATION
The build module merges extraction dictionaries into a NetworkX graph. Before this happens, the validation module checks every extraction against the schema and returns a list of error strings, or raises an exception when the assert variant is used. Validation guarantees that the graph builder only receives well-formed nodes and edges and provides a clear place to detect extractor bugs. The builder also deduplicates nodes and edges, folds aliases, mints external stub nodes for references to packages that are not part of the scan, and refuses to emit an edge whose endpoints are not present in the active graph.
3.3.4 CLUSTERING AND ANALYSIS MODULE
The cluster module partitions the graph into communities and returns a dictionary from a community identifier to its member nodes, without changing the graph. The analysis module contains sibling functions rather than a single entry point. The function god_nodes identifies nodes with very high connectivity. The function surprising_connections finds edges that link otherwise distant communities. The function find_import_cycles detects circular imports. The function graph_diff compares an old and a new graph. The function suggest_questions proposes questions that a reader might ask about the graph; it interleaves candidates across several question types before applying its result limit, so that ambiguous relationships cannot hide bridge, inferred-relationship, isolation and low-cohesion signals.
3.3.5 REPORTING AND EXPORT MODULE
The report module generates GRAPH_REPORT.md from the graph, its communities, cohesion scores and community labels. The export module offers one function per format: JSON for persistence and interchange, HTML for interactive viewing, SVG for static pictures, GraphML for graph tools, Obsidian for note-taking vaults, Canvas for visual boards and Cypher for graph databases. The wiki module writes one Markdown article per community plus an index, and the call-flow module writes a Mermaid architecture and call-flow page.
3.3.6 CACHE MODULE
Extraction can be expensive for files that need an external semantic pass. The cache module therefore stores previously extracted nodes, edges and hyperedges and, given a list of files, returns the cached results together with the list of files that still need extraction. The same cache stores the Abstract Syntax Tree payload of unchanged files, which the watcher replays as read-only resolution context so that a changed caller can still be resolved against unchanged callees.
3.3.7 INGESTION AND SECURITY MODULE
External input is the main attack surface of a local tool. The ingestion module saves a file fetched from a URL into the corpus directory. Before and during this operation the security module validates the URL, allows only the http and https schemes, blocks redirects to file URLs, blocks private, loopback, link-local and cloud-metadata addresses, fetches content with a size cap and a timeout, and checks that a graph file path resolves inside the output directory. Node labels are sanitised by removing control characters and limiting their length. The security policy and threat model are documented in SECURITY.md in the repository.

3.3.9 WATCHER AND HEALING MODULE
The watcher runs in the background when the MCP server starts. It debounces save, create, delete and rename events so that a burst of editor activity triggers one update. It re-parses only the affected files for locally parseable code and Markdown, compares the previous and the refreshed node sets, and records edges whose endpoints disappeared as BROKEN, with the missing node, its location and the reason. Broken references are kept as graph metadata and are never represented as phantom nodes. When a missing node reappears the broken edge is restored, and a unique same-file, same-location match can heal a symbol rename. Finally the persisted graph is updated atomically and the in-memory graph in the MCP server is refreshed. The debounce interval is configurable with the environment variable CODE2GRAPH_WATCH_DEBOUNCE; its default in the MCP server is 0.75 seconds, whereas the standalone watch function in watch.py takes a debounce argument whose default is 3.0 seconds.
3.3.10 BENCHMARK AND DIAGNOSTIC MODULES
The benchmark module compares the number of tokens in the whole corpus with the number of tokens in a retrieved subgraph. The diagnostics module reports the risk of same-endpoint edge collapse in a graph file, which is a real hazard because graph.json is stored undirected. The affected module performs a reverse traversal from a symbol to list the nodes that a change may impact, and the reflect module aggregates saved question-and-answer outcomes into a deterministic lessons document.
